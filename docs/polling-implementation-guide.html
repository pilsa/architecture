01개요와 보장 범위

핵심 메커니즘: 범위 청크 + 리스

이 설계의 모든 정합성과 동시성은 아래 세 장치에서 나옵니다. 나머지 구성요소(Reaper, Sweep 등)는 이 장치가 계속 돌도록 지키는 보조 역할입니다.

① 범위 청크

커서 키 (created_at, pk…) 공간을 겹치지 않는 (시작, 종료] 구간으로 자릅니다. Planner가 CAS로 계획HWM을 한 칸씩 전진시키므로 구간 사이에 겹침과 빈틈이 없습니다. → 중복 조회 없음, 읽기 증폭 없음

② 리스

워커는 SKIP LOCKED로 청크 하나를 기한을 정해 가져갑니다. pod가 죽으면 기한이 지난 청크를 다른 워커가 다시 가져갑니다. → pod 수와 무관하게 확장, 장애 자동 복구

③ fencing 완료

claim할 때마다 리스토큰이 증가합니다. 멱등·아웃박스 기록과 토큰 조건의 DONE 갱신을 한 트랜잭션으로 묶어, 토큰이 바뀌었으면 전부 롤백합니다. → 좀비 워커가 있어도 정확히 한 번

원리는 04장, 테이블은 05장, SQL은 08장에서 자세히 다룹니다.

입력 · 출력 · 목표

입력

읽기 복제본(PostgreSQL 물리 복제)에 있는 append-only 소스 테이블 N개. PK는 대부분 varchar 복합키.

앱 DB의 멱등 테이블과 아웃박스(기존 구현). Kafka 발행은 기존 아웃박스 릴레이가 담당.

02온보딩 필수조건

소스 테이블 하나를 폴링 대상으로 추가하려면 아래 조건을 모두 만족해야 합니다. 하나라도 지킬 수 없는 테이블은 폴링 방식으로 누락 없음을 보장할 수 없으므로, CDC(논리 복제) 대상으로 분류합니다.

가장 중요한 조건: 쓰기 트랜잭션 시간 상한

created_at = now()는 커밋 시각이 아니라 트랜잭션 시작 시각입니다. 시작한 지 오래된 트랜잭션이 늦게 커밋되면, 그 행은 커서가 이미 지나간 자리에 나타나 영구 누락됩니다. 그래서 primary 쓰기 트랜잭션의 최대 길이 B를 강제하고 safety_lag > B + 여유로 설정해야 합니다.

04작동 원리

4.1 커서 키: (created_at, pk1, …, pkn)

varchar PK는 삽입 순서와 무관한 위치에 새 행이 들어갑니다. 그래서 PK만으로 만든 커서(pk > cursor)는 새 행을 놓칩니다. 이 설계는 단조 증가하는 created_at을 맨 앞에 두고, PK는 같은 시각의 행들 사이 순서를 정하는 데만 씁니다.

PostgreSQL의 row 비교 (a, b, c) > (x, y, z)는 왼쪽부터 사전식으로 비교하고, 같은 순서의 B-tree 인덱스를 Index Cond로 사용합니다. 커서 튜플 전체가 유일하므로 (from, to] 구간은 서로 겹치지 않습니다. 한 트랜잭션에서 수천 행을 일괄 INSERT해 created_at이 모두 같아도 PK 순서로 정확히 나뉩니다.

4.2 안전 상한선 safe_ts

정의
safe_ts   = pg_last_xact_replay_timestamp() − safety_lag     (복제본에서 계산)
조건      : safety_lag ≥ B + 여유      (B = primary 쓰기 TX 최대 길이, 02장 P3)
청크 대상 : created_at < safe_ts 인 행만

이 조건이 누락을 막는 이유는 다음과 같습니다.

  1. 어떤 행의 created_at = c는 그 행을 쓴 트랜잭션 T의 시작 시각입니다. 필수조건 P3에 따라 T의 커밋 시각은 c + B보다 이릅니다.
  2. c < safe_ts = replay_ts − lag이고 lag ≥ B이므로, T의 커밋 시각은 replay_ts보다 이릅니다.
  3. 물리 복제본은 WAL을 커밋 순서대로 재생합니다. replay_ts는 이미 재생된 마지막 커밋의 primary 시각이므로, 그보다 먼저 커밋된 T도 이미 재생되어 보이는 상태입니다.
  4. 따라서 created_at < safe_ts인 행은 조회 시점에 모두 보이고, 이후에 새로 나타나지 않습니다. 커서가 지나간 자리는 다시 채워지지 않습니다.

WAL 안에서 커밋 타임스탬프가 아주 미세하게 역전되는 현상과 primary 시계 보정은 "여유"로 흡수합니다. 복제 지연이 생기면 replay_ts도 같이 늦어지므로 결과는 늘 보수적입니다. primary에 커밋이 없는 유휴 상태에서는 replay_ts가 멈춰 청크화도 멈춥니다. 이는 정확성을 위해 의도한 동작이고, 실시간 유입이 있으면 문제가 되지 않습니다.

쓰면 안 되는 보완책

pg_last_wal_receive_lsn() = pg_last_wal_replay_lsn()일 때 복제본의 now()를 기준으로 쓰는 방법은 금지합니다. 받은 WAL을 모두 재생했다는 뜻일 뿐, primary에 오래 열려 있는 트랜잭션이 없다는 보장이 아닙니다. hot_standby_feedback도 가시성 갭과는 관계없는 설정입니다.

4.3 청크와 Planner CAS

Planner는 계획HWM(마지막으로 잘린 커서 키) 다음부터 safe_ts 미만 범위에서 커서 순서로 최대 청크크기개 행을 세고, 마지막 행의 커서 키를 다음 경계로 정합니다. 경계값은 복제본에서 col::text로 받아 text[] 그대로 저장합니다. 애플리케이션은 이 값을 해석하거나 비교하지 않습니다.

정확성은 오직 CAS로 보장합니다. 앱 DB의 짧은 트랜잭션 하나에서 계획HWM = 조회 전에 읽은 값을 조건으로 HWM을 새 경계로 바꾸고, 같은 트랜잭션에서 청크를 INSERT합니다. 여러 pod가 같은 HWM에서 동시에 조회해도 CAS 승자 하나만 커밋하고, 진 쪽은 결과를 버립니다. 그래서 겹치거나 건너뛰는 구간이 생기지 않습니다. Planner 리스(소유자, 만료일시)는 중복 조회를 줄이는 최적화일 뿐입니다.

복제본 조회는 앱 DB 트랜잭션 밖에서 실행합니다. 이렇게 하면 앱 DB 커넥션과 행 잠금을 복제본 I/O 동안 붙잡지 않습니다.

4.4 claim · 리스 · fencing

Worker는 FOR UPDATE SKIP LOCKED로 READY 청크나 리스가 만료된 CLAIMED 청크 하나를 잠그고, 같은 문장에서 리스토큰 + 1, 소유자, 만료일시, 시도횟수 + 1을 기록한 뒤 바로 커밋합니다. READ COMMITTED에서 경합이 생기면 PostgreSQL이 최신 행 버전으로 조건을 다시 평가(EvalPlanQual)합니다. 잠긴 행은 건너뛰므로 두 워커가 같은 청크를 가져가는 일이 없습니다.

완료 트랜잭션은 [멱등 INSERT → 신규분만 아웃박스 INSERT → WHERE 리스토큰 = 내 토큰 AND 상태 = 'CLAIMED' 조건의 DONE 갱신]을 하나로 묶습니다. 마지막 UPDATE가 0행이면 예외를 던져 전체를 롤백합니다. 리스가 만료되어 다른 워커가 재claim한 경우, 늦게 깨어난 워커(좀비)의 기록은 이렇게 남지 않습니다. 동시에 같은 키를 INSERT하는 경우는 멱등 테이블의 unique 제약이 직렬화합니다.

4.5 불변식

구현과 테스트는 아래 불변식을 기준으로 검증합니다.

한 에포크 안에서 청크들은 (시작점, 계획HWM]을 겹침과 빈틈 없이 분할한다. CAS가 HWM을 직렬로만 전진시키기 때문이다.

계획HWM 이하의 행은 계획 시점에 모두 보이고, 이후에 새로 생기지 않는다. 4.2와 필수조건 P1~P4가 근거다.

소스 행 하나는 앱 DB에 많아야 한 번 반영된다. fencing과 멱등 unique 제약이 같은 트랜잭션 안에 있기 때문이다.

모든 청크는 결국 DONE이나 DEAD에 도달한다. 리스 만료로 재claim되고, Reaper가 시도 횟수를 다 쓴 청크를 DEAD로 바꾸기 때문이다.

DEAD가 하나라도 생기면 해당 소스의 Planner가 멈추고 알람이 울린다. 처리되지 않은 빈틈을 남긴 채 계속 전진하지 않는다.

07청크 상태 전이

#전이주체SQL 조건 요지함께 일어나는 일
①READY → CLAIMEDWorkerattempts < max, next_attempt_at 경과, 소스가 HARD_PAUSED가 아님, SKIP LOCKED토큰+1, 시도+1, 리스 설정
②CLAIMED → DONEWorkerlease_token = 내 토큰 AND status = 'CLAIMED' AND source_epoch = 내 에포크같은 트랜잭션에서 멱등과 아웃박스 기록. 0행이면 롤백
③CLAIMED → READYWorker토큰 일치, attempts < max리스 해제, 오류 기록, next_attempt_at 설정
④CLAIMED·READY → DEADWorker, Reaper토큰 일치이면서 attempts >= max(Worker), 또는 만료이면서 attempts >= max(Reaper)같은 트랜잭션에서 소스를 SOFT_PAUSED로 바꾸고 알람
⑤CLAIMED → CLAIMEDWorker재claim: lease_until < now. heartbeat: 토큰·소유자 일치이고 아직 유효함재claim이면 토큰+1이 되어 기존 소유자의 완료가 차단됨

DONE과 DEAD는 종료 상태입니다. 상태를 되돌리지 않고, 재처리는 새 청크나 재처리 요청으로 만듭니다.

08처리 흐름과 SQL

예시 소스는 sales.order_line이고, 커서는 (created_at timestamptz, order_no varchar "C", line_no varchar "C")입니다. 실제 SQL은 09장의 렌더러가 소스 정의로 생성합니다. 표기법: :name은 바인드 변수, 복제본과 앱 DB는 실행 위치입니다.

8.1 Planner

  1. 앱 DB Planner 리스를 짧은 단독 트랜잭션으로 획득합니다. 0행이면 다른 pod가 담당 중이므로 이번 주기는 건너뜁니다.
  2. 복제본 safe_ts를 구합니다. replay_ts가 null이면 건너뜁니다.
  3. 복제본 다음 경계를 조회합니다. 트랜잭션 밖에서 실행합니다.
  4. 앱 DB CAS로 HWM을 전진시키고 청크를 INSERT합니다. 둘이 한 트랜잭션입니다. 경계 조회 결과가 청크크기만큼 꽉 차 있으면 3단계부터 반복하고(따라잡기 모드), 아니면 다음 주기까지 쉽니다(꼬리 추적 모드).
① Planner 리스 · 앱 DB
UPDATE poll_source
SET planner_owner = :owner,
    planner_lease_until = statement_timestamp() + make_interval(secs => :planner_lease_sec)
WHERE source_id = :source_id
  AND run_state = 'ACTIVE'
  AND (planner_lease_until IS NULL
       OR planner_lease_until < statement_timestamp()
       OR planner_owner = :owner)
RETURNING source_epoch, config_hash, planned_hwm, initial_start_ts,
          chunk_size, max_pending, safety_lag_sec;
② safe_ts · 복제본
SELECT pg_is_in_recovery()                                         AS in_recovery,     -- false면 즉시 중단(잘못된 엔드포인트)
       pg_last_xact_replay_timestamp()                             AS replay_ts,
       pg_last_xact_replay_timestamp() - make_interval(secs => :lag) AS safe_ts;
③ 경계 조회 · 복제본 (planned_hwm이 '{}'면 row 비교 대신 created_at >= :initial_start_ts)
WITH batch AS (
  SELECT created_at, order_no, line_no
  FROM "sales"."order_line"
  WHERE ("created_at", "order_no" COLLATE "pg_catalog"."C", "line_no" COLLATE "pg_catalog"."C")
      > (CAST(:a1 AS timestamptz),
         CAST(:a2 AS varchar) COLLATE "pg_catalog"."C",
         CAST(:a3 AS varchar) COLLATE "pg_catalog"."C")
    AND "created_at" < CAST(:safe_ts AS timestamptz)
  ORDER BY "created_at", "order_no" COLLATE "pg_catalog"."C", "line_no" COLLATE "pg_catalog"."C"
  LIMIT :chunk_size
)
SELECT ARRAY[created_at::text, order_no::text, line_no::text] AS to_key,
       created_at                                             AS to_created_at,
       (SELECT count(*) FROM batch)                            AS row_count
FROM batch
ORDER BY created_at DESC, order_no COLLATE "pg_catalog"."C" DESC, line_no COLLATE "pg_catalog"."C" DESC
LIMIT 1;                                   -- 결과 없음 = 새 데이터 없음
④ CAS 확정 · 앱 DB · 단일 트랜잭션
UPDATE poll_source AS s
SET planned_hwm = :to_key, planned_created_at = :to_created_at, updated_at = statement_timestamp()
WHERE s.source_id    = :source_id
  AND s.source_epoch = :source_epoch
  AND s.config_hash  = :config_hash
  AND s.run_state    = 'ACTIVE'
  AND s.planned_hwm  = :expected_hwm                     -- CAS
  AND (SELECT count(*) FROM poll_chunk c
       WHERE c.source_id = s.source_id AND c.source_epoch = s.source_epoch
         AND c.status IN ('READY','CLAIMED')) < s.max_pending;
-- 위 UPDATE가 정확히 1행일 때만 계속하고, 아니면 ROLLBACK 후 결과를 버린다
INSERT INTO poll_chunk (source_id, source_epoch, config_hash, from_key, to_key, to_created_at)
VALUES (:source_id, :source_epoch, :config_hash, :expected_hwm, :to_key, :to_created_at);
COMMIT;

8.2 Worker

WITH candidate AS MATERIALIZED (
  SELECT c.chunk_id
  FROM poll_chunk c
  JOIN poll_source s ON s.source_id = c.source_id AND s.source_epoch = c.source_epoch
  WHERE c.source_id = :source_id
    AND s.run_state <> 'HARD_PAUSED'
    AND c.attempts < s.max_attempts
    AND (   (c.status = 'READY'   AND (c.next_attempt_at IS NULL OR c.next_attempt_at <= statement_timestamp()))
         OR (c.status = 'CLAIMED' AND c.lease_until < statement_timestamp()))
  ORDER BY c.chunk_id
  LIMIT 1
  FOR UPDATE OF c SKIP LOCKED
)

8.4 Sweep · Replay

sweep의 상한은 완료HWM입니다

계획HWM을 상한으로 잡으면 아직 처리 중인 청크의 행이 누락으로 오탐됩니다. sweep은 정상 경로를 보장하는 장치가 아니라 필수조건 위반을 탐지하는 장치입니다. 누락건수가 0보다 크면 writer 트랜잭션 상한(P3)이 깨졌다는 뜻이므로 즉시 알람을 보냅니다.

9.3 TextArrayTypeHandler

MyBatis 기본 ArrayTypeHandler는 배열 타입을 VARCHAR로 만들고 List를 지원하지 않습니다. text[] 전용 핸들러를 쓰고, Java에서 배열 리터럴 문자열을 직접 조립하지 않습니다.

TextArrayTypeHandler.java
@MappedTypes(String[].class)
@MappedJdbcTypes(value = JdbcType.ARRAY, includeNullJdbcType = true)
public class TextArrayTypeHandler extends BaseTypeHandler<String[]> {

  @Override
  public void setNonNullParameter(PreparedStatement ps, int i, String[] v, JdbcType t) throws SQLException {
    ps.setArray(i, ps.getConnection().createArrayOf("text", v));
  }
  @Override public String[] getNullableResult(ResultSet rs, String c) throws SQLException { return read(rs.getArray(c)); }
  @Override public String[] getNullableResult(ResultSet rs, int i) throws SQLException { return read(rs.getArray(i)); }
  @Override public String[] getNullableResult(CallableStatement cs, int i) throws SQLException { return read(cs.getArray(i)); }

  private static String[] read(Array a) throws SQLException {
    if (a == null) return null;
    try { return (String[]) a.getArray(); } finally { a.free(); }
  }
}

9.4 SQL 렌더러와 기동 검증

  • 테이블, 컬럼, 타입, collation 같은 식별자는 기동 시 한 번 렌더링해 SourceSpec에 SQL 조각으로 보관합니다. 매퍼의 ${}에는 이 조각만 넣습니다. 식별자는 큰따옴표로 감싸고 내부의 "는 두 번 씁니다. 타입은 allowlist enum에서만 고릅니다.
  • 값은 항상 #{}로 바인딩하고 CAST(#{p.value} AS 타입) COLLATE … 형태로 씁니다.
  • 기동 순서는 다음과 같습니다.
    1. 복제본에서 pg_is_in_recovery() = true인지, SHOW TimeZone = UTC인지, SHOW DateStyle이 ISO로 시작하는지 확인
    2. 커서 인덱스 카탈로그 검증(아래 SQL)
    3. 각 커서 타입의 v = (v::text)::type 왕복 표본 검증
    4. YAML에서 계산한 설정해시와 poll_source.config_hash 비교. 다르면 기동을 거부하고 에포크 변경 절차(11장)로 안내
SqlRenderer 핵심
public final class SqlRenderer {
  private static final Map<String, String> TYPES = Map.of(
      "timestamptz", "timestamptz", "timestamp", "timestamp", "varchar", "varchar",
      "text", "text", "int4", "integer", "int8", "bigint", "uuid", "uuid");

  public static String ident(String name) {                  // "a""b"
    return '"' + name.replace("\"", "\"\"") + '"';
  }
  public static String qualified(String dotted) {            // pg_catalog.C → "pg_catalog"."C"
    return Arrays.stream(dotted.split("\\.")).map(SqlRenderer::ident).collect(joining("."));
  }
  public static String castType(String typeName) {
    String t = TYPES.get(typeName);
    if (t == null) throw new IllegalStateException("허용되지 않은 커서 타입: " + typeName);
    return t;
  }
  /** 컬럼 표현식: "order_no" COLLATE "pg_catalog"."C" */
  public static String colExpr(CursorColumn c) {
    return ident(c.name()) + (c.collation() == null ? "" : " COLLATE " + qualified(c.collation()));
  }
}

/** 바인딩 단위: value는 #{}로, castSql·collateSql은 렌더링된 조각으로 */
public record CursorParam(String value, String castSql, String collateSql) {}
기동 검증 · 복제본에서 실행
SELECT a.attname, a.attnotnull, format_type(a.atttypid, a.atttypmod) AS type,
       am.amname, i.indisvalid, i.indisready, i.indislive,
       i.indpred IS NULL AS not_partial, i.indexprs IS NULL AS no_expr,
       (i.indoption[k.pos - 1] & 1) = 0 AS is_asc,
       coll.collname, coll.collisdeterministic,
       coll.collversion IS NOT DISTINCT FROM pg_collation_actual_version(coll.oid) AS collation_version_ok
FROM pg_index i
JOIN pg_class ci ON ci.oid = i.indexrelid
JOIN pg_am am    ON am.oid = ci.relam
CROSS JOIN LATERAL generate_series(1, i.indnkeyatts) AS k(pos)
JOIN pg_attribute a ON a.attrelid = i.indrelid AND a.attnum = i.indkey[k.pos - 1]
LEFT JOIN pg_collation coll ON coll.oid = i.indcollation[k.pos - 1]
WHERE i.indexrelid = to_regclass(:qualified_index_name)
ORDER BY k.pos;
-- 통과 조건: btree, valid·ready·live, partial·expression 아님, 키 수 = 커서 컬럼 수,
--           모든 키가 NOT NULL·ASC, 순서·타입·collation이 source_cursor_column과 일치,
--           문자열 키는 collisdeterministic AND collation_version_ok

9.6 서비스 코드 뼈대

WorkerLoop · CompletionService
// WorkerLoop: pod마다 worker-threads개를 실행. 종료 신호를 받으면 새 claim을 멈추고 진행 중인 청크만 마무리
while (running.get()) {
  Optional<ClaimedChunk> claimed = claimService.claim(spec, ownerId);     // 앱 DB 단독 트랜잭션
  if (claimed.isEmpty()) { backoff.sleep(); continue; }                     // 100ms → 1s
  backoff.reset();
  ClaimedChunk c = claimed.get();
  try (Heartbeat hb = heartbeats.start(c)) {                                // lease/3 주기, 실패 시 hb.lost()=true
    List<SourceRow> rows = reader.readAll(spec, c, hb);                    // 복제본, 페이지 반복, 페이지마다 hb 확인
    completion.complete(spec, c, rows);                                     // 앱 DB 단일 트랜잭션
    metrics.done(c, rows.size());
  } catch (FencedException | LeaseLostException e) {
    metrics.fenced(c);                                                      // 다른 워커가 가져감. 아무것도 하지 않음
  } catch (Exception e) {
    failure.fail(c, e);                                                     // 재시도 가능하면 READY, 아니면 DEAD + 소스 일시정지
  }
}

@Service
public class CompletionService {
  @Transactional(transactionManager = "appTxManager")                     // 앱 DB 하나의 커넥션·트랜잭션
  public void complete(SourceSpec spec, ClaimedChunk c, List<SourceRow> rows) {
    int inserted = rows.isEmpty() ? 0 : outboxMapper.insertIdempotentWithOutbox(
        spec.id(), spec.eventType(), keys(rows), payloads(rows));
    int updated = chunkMapper.markDone(c.chunkId(), c.leaseToken(), c.sourceEpoch(), rows.size(), inserted);
    if (updated != 1) throw new FencedException(c);                         // RuntimeException이므로 전체 롤백
  }
}
구현할 때 흔한 실수
  • FencedException을 트랜잭션 안에서 catch하고 정상 반환하면 좀비 워커의 기록이 커밋됩니다. 예외는 반드시 트랜잭션 경계 밖으로 던집니다.
  • 복제본 조회를 @Transactional(appTxManager) 안에서 하면 앱 DB 트랜잭션이 길어집니다. 조회는 완료 트랜잭션보다 먼저, 밖에서 합니다.
  • 경계값을 OffsetDateTime이나 LocalDateTime으로 받아 다시 넘기면 정밀도와 타임존 문제가 생깁니다. 항상 String[]으로 왕복합니다.
  • 복제본 오류 SQLSTATE 40001(recovery conflict로 취소), 57014(statement timeout)은 같은 페이지를 재시도합니다. 백오프와 지터를 넣고, 재시도 예산을 넘기면 실패 처리합니다.

11.2 운영 절차 (runbook)

소스 추가

필수조건 P1~P8 확인 → primary에 커서 인덱스를 CONCURRENTLY로 생성 → 복제본에서 EXPLAIN 확인 → YAML 추가(초기시작일시 지정) → 낮은 워커 수로 활성화 → 지연과 sweep 누락 0 확인 후 증설

일시정지

SOFT_PAUSED는 Planner만 멈추고 남은 청크를 소진합니다. HARD_PAUSED는 신규 claim까지 막고, 진행 중인 청크는 완료되거나 리스가 만료되기를 기다립니다.

DEAD 처리

원인 확인 및 수정 → DEAD 청크를 이력으로 이관(DELETE … RETURNING → INSERT) → 같은 범위로 새 READY 청크 등록(attempts = 0) → run_state = 'ACTIVE'. DEAD 원본은 이력에 그대로 남습니다.

HWM 리셋 · 커서 정의 변경

HARD_PAUSED → 리스 만료 대기 → 한 트랜잭션에서 [활성 청크 전부 이력 이관 + source_epoch + 1, 새 설정해시, 새 HWM] 커밋 → ACTIVE. 이전 에포크 워커의 완료 처리는 0행이 되어 롤백됩니다. 멱등 키에 에포크가 없으므로 다시 읽어도 이벤트는 재발행되지 않습니다.

이벤트 재발행

멱등 테이블이 막으므로 재처리만으로는 재발행되지 않습니다. 재발행이 필요하면 별도 replay generation과 event id 정책을 세우고 컨슈머 쪽과 합의한 뒤 진행합니다.

복제본 교체 · 업그레이드

새 엔드포인트에서 pg_is_in_recovery, 서버 버전, 지연, collation 버전, 인덱스 정의를 검증합니다. OS·ICU·PG 메이저 업그레이드로 collation 순서가 바뀌었다면 HARD_PAUSED → REINDEX(소스팀) → FULL sweep 또는 새 에포크로 진행합니다.
