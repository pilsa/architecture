01시스템 구성

구성요소 역할
rdt-db CDC로 복제된 읽기 전용 DB. 소스 테이블(예: 고객일별평잔, 입출금거래내역)이 있다. 프로모션 가입자와 미가입자의 데이터가 섞여 있다
prm-db 프로모션, 리워드그룹, 리워드항목, 가입고객, 디텍터 설정, 멱등, 아웃박스 테이블. detector와 provider가 같이 사용한다
promotion-detector 소스 테이블을 읽고, 리워드 대상 이벤트를 골라 아웃박스에 넣는다. rdt-db에 접근하는 유일한 애플리케이션
promotion-provider 리워드 엔진. 아웃박스 메시지를 받아 누적·한도·산정·지급을 처리한다. rdt-db를 조회하지 않는다
admin 관리자가 프로모션, 리워드그룹, 디텍터 설정을 입력한다
가입 API 고객식별자 + 가입 프로모션을 받아 가입고객 테이블에 넣는다 
[admin] ──▶ 디텍터 설정 · 프로모션 · 리워드그룹 · 리워드항목 (prm-db)
[가입 API] ──▶ 프로모션가입고객 (prm-db)

rdt-db ──읽기──▶ [promotion-detector] ──▶ 디텍터멱등내역 ──▶ 디텍터아웃박스 ──relay──▶ [promotion-provider]
                     │  설정: 캐시                                                    │
                     └─ 가입 조회: prm-db                                             └─▶ 수신내역 · 지급

02확정 사항

# 내용
1 디텍터는 소스 테이블과 1:1로 정의한다. 한 번 읽은 결과를 여러 프로모션·리워드그룹이 함께 쓴다
2 누적, 한도, 1인 1회, 횟수 조건은 리워드 엔진(provider)이 맡는다
3 리워드를 무엇으로 얼마나 줄지는 provider가 정한다. 디텍터는 산정에 필요한 값만 아웃박스로 넘긴다
4 아웃박스 입력 전 디텍터멱등내역에 먼저 INSERT를 시도해 중복을 막는다. PK는 IDMPT_KEY VARCHAR(200)이고 값은 소스 테이블의 비즈니스 설계에 따라 정한다
5 소급 처리는 없다. 가입하지 않은 상태에서 조회된 행은 지급 대상이 아니다
6 고객(가입) 필터는 prm-db 조회, 설정 정보는 캐시를 쓴다

03역할과 책임 분리

기준: 행 하나만 보고 판단할 수 있으면 디텍터, 과거 이력이나 다른 행이 필요하면 provider.

책임 detector provider
소스 읽기 (rdt-db) ✅ ❌
가입 여부 + 이벤트일시 ≥ 가입일시 ✅
프로모션 기간 · 트리거 유효기간 (이벤트일시 기준) ✅ 지급 시점 재검증
행 단위 조건 (금액 이상, 거래유형 일치 등) ✅
요청 중복 방지 ✅ 디텍터멱등내역 ✅ 수신 멱등
산정 입력값 전달 ✅ 페이로드
누적 · 한도 · 1인 1회 · 횟수 ✅
같은 프로모션 내 그룹 간 배타 · 우선순위 ✅
리워드항목 선택 · 금액 산정 · 재화 지급 ✅
이벤트 순서 해석 이벤트일시 · 원천순번 제공 ✅ 이벤트일시 기준 판단
  • 디텍터는 상태를 갖지 않는다. 그래서 재처리, 병렬 처리, pod 확장이 단순하다.
  • provider는 조건을 통과한 요청만 받는다. 행 평가를 provider로 넘기면 고객일별평잔만으로도 매일 "가입자 수 × 그룹 수"만큼의 요청이 아웃박스를 지나간다.
  • 조건 정의는 저장 위치로 나눈다. 관리자 화면에서는 리워드그룹 화면 한 곳에서 입력하되, 행 단위 조건은 디텍터트리거조건에, 누적·한도 조건은 리워드그룹(기존)에 저장한다.

04처리 흐름

4.1 청크 처리 순서: 설정 → 행 평가 → 가입 조회

행 평가와 가입 확인은 둘 다 AND 조건이라 순서를 바꿔도 결과가 같다. 그래서 비용이 싼 쪽을 먼저 한다.

단계 위치 비용 내용
① 설정 캐시 0 디텍터의 유효한 트리거 목록, 미리 컴파일한 조건, 트리거 → 프로모션 매핑
② 행 평가 메모리 μs 단위 행 × 트리거마다 조건을 평가해 후보 (행, 트리거)를 만든다. 후보가 0건이면 종료 (DB 조회 생략)
③ 가입 조회 prm-db 1회 후보 행의 고객번호 × 후보 프로모션만 조회
④ 결합 메모리 μs 단위 가입 상태 = ACTIVE ∧ 이벤트일시 ≥ 가입일시 ∧ 프로모션 기간 ∧ 트리거 유효기간
⑤ 기록 prm-db 1 TX ms 단위 (이벤트일시, 원천순번) 순으로 정렬 → 디텍터멱등내역 INSERT(충돌 시 무시) → 성공한 건만 디텍터아웃박스 INSERT
SQL
-- ③ 가입 조회 (후보만)
SELECT CUST_NO, PRMT_ID, JOIN_DTM
FROM PRMT_CUST
WHERE CUST_NO = ANY(:candidateCusts)
  AND PRMT_ID = ANY(:candidatePrmts)
  AND STTS_CD = 'ACTIVE';
  • 조건을 소스 조회 SQL(WHERE)에 넣지 않는다. 행 하나를 여러 트리거가 함께 쓰므로, 조회 단계에서 거르면 다른 트리거의 대상 행까지 잘린다.
  • 설정 캐시: 몇 초마다 디텍터기본.설정버전만 확인하고, 바뀌었을 때만 설정 전체를 다시 읽는다. 청크 하나를 처리하는 동안은 처리 시작 시점의 버전으로 고정한다.

4.2 예시 1: 고객일별평잔 (행 1개 → 2건)

  • 조회된 행: 고객 C001, 평잔 2천만 원
  • C001은 P1, P2에 가입되어 있다.
트리거 리워드그룹 조건 평가 가입 결과
T1 P1-GROUP1 평잔 ≥ 100만 통과 P1 가입 아웃박스 1건
T2 P2-GROUP1 평잔 ≥ 1,000만 통과 P2 가입 아웃박스 1건

멱등키에 리워드그룹이 들어가므로 두 건이 서로 막히지 않는다.

4.3 예시 2: 입출금거래내역 (행 10개 → 3건)

  • 고객 C002가 거래 10건. C002는 P3에 가입되어 있다.
트리거 리워드그룹 디텍터가 평가하는 조건 provider가 판단하는 조건
T3 P3-GROUP1 거래유형 = 일반출금 ∧ 금액 ≥ 1만 —
T4 P3-GROUP2 거래유형 = 자동이체 ∧ 금액 ≥ 1만 —
T5 P3-GROUP3 거래유형 = 입금 1건 (1인 1회)
  • 각 조건에 맞는 거래가 1건씩이면 3건이 입력되고 7건은 탈락한다.
  • 입금이 2건이면 디텍터는 T5 요청을 2건 보내고, provider가 1인 1회 규칙으로 두 번째 요청을 REJECTED로 처리한다.
  • 순서 보장 범위:
    • 디텍터는 청크 안에서만 (이벤트일시, 원천순번) 순으로 입력한다.
    • 청크는 여러 pod가 병렬로 처리하므로, 청크 사이의 아웃박스 입력 순서는 거래 순서와 다를 수 있다.
    • 그래서 provider는 도착 순서가 아니라 페이로드의 이벤트일시와 원천순번으로 순서를 판단한다.
  • 행 하나가 같은 프로모션의 그룹 여러 개를 통과하면 디텍터는 그룹마다 보낸다. 그중 무엇을 줄지(배타 규칙)는 provider가 정한다.

4.4 멱등키 규칙

IDMPT_KEY = {디텍터ID}|{소스 비즈니스키}|{리워드그룹ID}

고객일별평잔   : D_AVGBAL|20261104|C001|P2-GROUP1        (기준일자 + 고객번호)
입출금거래내역 : D_TXN|1002003004|20261105|000123|P3-GROUP1 (계좌 + 거래일자 + 거래일련번호)
  • 리워드그룹ID는 반드시 넣는다. 빠지면 예시 1의 두 번째 건이 멱등 충돌로 막힌다.
  • 소스 비즈니스키는 디텍터필드.멱등키순서로 정한 컬럼을 순서대로 이어 붙인다.
  • 합친 길이가 200자를 넘을 수 있으면 소스 비즈니스키 부분만 SHA-256(64자)으로 바꾼다.
  • 디텍터아웃박스.요청ID와 프로바이더수신내역.요청ID도 같은 값을 쓴다. 원천 행 → 아웃박스 → 지급 결과를 키 하나로 추적할 수 있다.

5.2 디텍터 설정

디텍터기본 (DTCT_BASE)

역할 디텍터 하나를 정의한다. 디텍터와 소스 테이블은 1:1이다.
키 PK DTCT_ID · UK (SRC_SCHM_NM, SRC_TBL_NM)
컬럼 타입 설명
디텍터ID (DTCT_ID) VARCHAR(32) 디텍터 식별자. 예: D_AVGBAL
디텍터명 (DTCT_NM) VARCHAR(100) 화면 표시명. 예: 고객일별평잔 디텍터
소스스키마명 (SRC_SCHM_NM) VARCHAR(64) rdt-db 스키마
소스테이블명 (SRC_TBL_NM) VARCHAR(64) rdt-db 소스 테이블
고객식별자필드 (CUST_FLD) VARCHAR(64) 소스의 고객번호 컬럼명
이벤트일시필드 (EVT_DTM_FLD) VARCHAR(64) 가입일시·기간 비교 기준 컬럼 (기준일자, 거래일시 등)
상태코드 (STTS_CD) VARCHAR(16) DRAFT 작성중 / ACTIVE 운영 / PAUSED 중지
설정버전 (CFG_VER) INT 설정 저장 시 +1. 디텍터 캐시 갱신 신호
변경자ID (CHG_ID) VARCHAR(64) 마지막 변경 관리자
변경일시 (CHG_DTM) TIMESTAMPTZ 마지막 변경 시각

디텍터필드 (DTCT_FLD)

역할 디텍터가 쓸 수 있는 소스 컬럼의 허용 목록이다. 컬럼마다 조건, 페이로드, 멱등키, 정렬 중 어디에 쓰는지 지정한다.
키 PK (DTCT_ID, FLD_NM)
컬럼 타입 설명
디텍터ID (DTCT_ID) VARCHAR(32) 소속 디텍터
필드명 (FLD_NM) VARCHAR(64) 소스 컬럼명. 예: AVG_BAL
필드한글명 (FLD_KOR_NM) VARCHAR(100) 화면 표시명. 예: 평잔금액
데이터유형코드 (DATA_TP_CD) VARCHAR(16) STR / NUM / DATE / DTM
조건사용여부 (COND_YN) CHAR(1) Y면 트리거 조건에 사용 가능
페이로드여부 (PAYLOAD_YN) CHAR(1) Y면 아웃박스에 값 전달 (산정 입력값)
멱등키순서 (IDMPT_KEY_ORD) SMALLINT 소스 비즈니스키 구성 순서. NULL이면 미포함
정렬순서 (SORT_ORD) SMALLINT 청크 안 정렬 순서 (원천순번). NULL이면 미사용

디텍터트리거 (DTCT_TRGR)

역할 디텍터와 리워드그룹을 연결한다. 한 번 읽은 행을 여러 리워드그룹에 나누는 단위다.
키 PK TRGR_ID · UK (DTCT_ID, RWD_GRP_ID) · IX (DTCT_ID, PRMT_ID)
컬럼 타입 설명
트리거ID (TRGR_ID) VARCHAR(32) 트리거 식별자
디텍터ID (DTCT_ID) VARCHAR(32) 데이터를 읽는 디텍터
리워드그룹ID (RWD_GRP_ID) VARCHAR(32) 연결할 리워드그룹 (기존 테이블)
프로모션ID (PRMT_ID) VARCHAR(32) 리워드그룹의 프로모션. 가입 조회용으로 중복 저장
유효시작일시 (VALID_STRT_DTM) TIMESTAMPTZ 이 시각 이후 이벤트부터 대상
유효종료일시 (VALID_END_DTM) TIMESTAMPTZ 이 시각 이후 이벤트는 제외. NULL이면 무기한
상태코드 (STTS_CD) VARCHAR(16) ACTIVE 운영 / PAUSED 중지
변경자ID (CHG_ID) VARCHAR(64) 마지막 변경 관리자
변경일시 (CHG_DTM) TIMESTAMPTZ 마지막 변경 시각

디텍터트리거조건 (DTCT_TRGR_COND)

역할 트리거의 행 단위 조건이다. 조건이 여러 개면 모두 AND로 묶는다. 누적·한도 조건은 넣지 않는다.
키 PK (TRGR_ID, COND_SEQ)
컬럼 타입 설명
트리거ID (TRGR_ID) VARCHAR(32) 소속 트리거
조건순번 (COND_SEQ) SMALLINT 조건 순서
필드명 (FLD_NM) VARCHAR(64) 비교할 소스 컬럼. 조건사용여부 = Y인 필드만
연산자코드 (OPR_CD) VARCHAR(8) EQ / NE / IN / NOT_IN / GE / GT / LE / LT / BETWEEN
조건값 (COND_VAL) VARCHAR(500) 비교값. IN은 콤마 목록, BETWEEN은 최소,최대

예시 데이터:

트리거ID 디텍터ID 리워드그룹ID 조건
T1 D_AVGBAL P1-GROUP1 AVG_BAL GE 1000000
T2 D_AVGBAL P2-GROUP1 AVG_BAL GE 10000000
T3 D_TXN P3-GROUP1 TXN_TP EQ 일반출금 · TXN_AMT GE 10000
T4 D_TXN P3-GROUP2 TXN_TP EQ 자동이체 · TXN_AMT GE 10000
T5 D_TXN P3-GROUP3 TXN_TP EQ 입금

디텍터설정이력 (DTCT_CFG_HIST)

역할 디텍터 설정을 저장할 때마다 전체 스냅샷을 남긴다. 어느 설정 버전으로 판정했는지 추적하는 데 쓴다.
키 PK (DTCT_ID, CFG_VER)
컬럼 타입 설명
디텍터ID (DTCT_ID) VARCHAR(32) 대상 디텍터
설정버전 (CFG_VER) INT 저장 당시 버전
설정스냅샷 (CFG_SNAPSHOT) JSONB 기본·필드·트리거·조건 전체
변경자ID (CHG_ID) VARCHAR(64) 변경 관리자
변경일시 (CHG_DTM) TIMESTAMPTZ 변경 시각

5.3 고객

프로모션가입고객 (PRMT_CUST)

역할 고객의 프로모션 가입 현재 상태다. 가입 API가 쓰고, 디텍터가 가입 필터로 조회한다.
키 PK (PRMT_ID, CUST_NO) · UK JOIN_REQ_ID · UK (CUST_NO, PRMT_ID) INCLUDE (STTS_CD, JOIN_DTM) — 디텍터 조회용 커버링 인덱스
컬럼 타입 설명
프로모션ID (PRMT_ID) VARCHAR(32) 가입한 프로모션
고객번호 (CUST_NO) VARCHAR(20) 고객식별자. 소스 테이블과 같은 형식
상태코드 (STTS_CD) VARCHAR(8) ACTIVE 가입 / LEFT 탈퇴
가입일시 (JOIN_DTM) TIMESTAMPTZ DB now(). 이 시각 이후 이벤트만 대상 (소급 없음)
탈퇴일시 (LEAVE_DTM) TIMESTAMPTZ 탈퇴 시각
가입요청ID (JOIN_REQ_ID) VARCHAR(64) 가입 API 중복 요청 방지
가입채널코드 (JOIN_CHNL_CD) VARCHAR(16) 가입 경로
변경일시 (CHG_DTM) TIMESTAMPTZ 마지막 변경 시각

설계 포인트: - 디텍터는 항상 "이 고객들이 어떤 프로모션에 가입했나"를 묻는다. 그래서 CUST_NO가 앞에 오는 인덱스가 핵심이다. INCLUDE로 상태와 가입일시를 인덱스에 담아 테이블을 읽지 않는 index-only scan이 되게 한다. - 가입이 계속 들어오므로 autovacuum을 공격적으로 설정한다. visibility map이 최신이어야 index-only scan이 유지된다. - 용량: 300만 명 × 평균 2~3개 = 600만~900만 행. 인덱스가 메모리에 올라가는 크기라 파티셔닝은 필요 없다.

프로모션가입고객이력 (PRMT_CUST_HIST)

역할 가입·탈퇴·재가입 이력이다. 감사와 분쟁 대응에 쓴다. 디텍터는 읽지 않는다.
키 PK HIST_ID · IX (CUST_NO, PRMT_ID)
컬럼 타입 설명
이력ID (HIST_ID) BIGSERIAL 이력 식별자
프로모션ID (PRMT_ID) VARCHAR(32) 대상 프로모션
고객번호 (CUST_NO) VARCHAR(20) 대상 고객
처리구분코드 (ACT_CD) VARCHAR(8) JOIN 가입 / LEAVE 탈퇴 / REJOIN 재가입
요청ID (REQ_ID) VARCHAR(64) API 요청 식별자
등록일시 (REG_DTM) TIMESTAMPTZ 처리 시각

5.4 디텍터 ↔ provider 연계

디텍터멱등내역 (DTCT_IDMPT_HIST)

역할 아웃박스에 넣기 전 먼저 INSERT를 시도해 같은 요청이 두 번 나가지 않게 막는다. 충돌하면 그 건은 건너뛴다.
키 PK IDMPT_KEY · 등록월 기준 파티션 (보관 기간이 지나면 파티션 삭제)
컬럼 타입 설명
멱등키 (IDMPT_KEY) VARCHAR(200) {디텍터ID}|{소스 비즈니스키}|{리워드그룹ID}
디텍터ID (DTCT_ID) VARCHAR(32) 생성한 디텍터
트리거ID (TRGR_ID) VARCHAR(32) 통과한 트리거
고객번호 (CUST_NO) VARCHAR(20) 대상 고객
이벤트일시 (EVT_DTM) TIMESTAMPTZ 소스 이벤트 시각
등록일시 (REG_DTM) TIMESTAMPTZ INSERT 시각

디텍터아웃박스 (DTCT_OUTBOX)

역할 detector → provider 리워드 생성 요청이다. 1행 = 소스 행 1개 × 리워드그룹 1개. 기존 relay가 발행한다.
키 PK OUTBOX_ID · UK REQ_ID · 발행 대기 부분 인덱스 · 등록월 기준 파티션
컬럼 타입 설명
아웃박스ID (OUTBOX_ID) BIGSERIAL 발행 순서 식별자
요청ID (REQ_ID) VARCHAR(200) = 멱등키. provider 수신 멱등 키
프로모션ID (PRMT_ID) VARCHAR(32) 대상 프로모션
리워드그룹ID (RWD_GRP_ID) VARCHAR(32) 대상 리워드그룹
고객번호 (CUST_NO) VARCHAR(20) 대상 고객. 메시지 키로 써서 고객별 순서 유지
디텍터ID (DTCT_ID) VARCHAR(32) 생성한 디텍터
트리거ID (TRGR_ID) VARCHAR(32) 통과한 트리거
이벤트일시 (EVT_DTM) TIMESTAMPTZ provider 순서 판단 기준
원천순번 (SRC_SEQ) VARCHAR(100) 같은 시각 이벤트의 순서 (거래일련번호 등)
소스비즈니스키 (SRC_BIZ_KEY) VARCHAR(150) 원천 행 추적용
페이로드 (PAYLOAD) JSONB 산정 입력값. 예: {"AVG_BAL": 20000000}
설정버전 (CFG_VER) INT 판정에 쓴 디텍터 설정 버전
발행상태코드 (PUB_STTS_CD) VARCHAR(8) READY / SENT (기존 relay 방식)
등록일시 (REG_DTM) TIMESTAMPTZ INSERT 시각

프로바이더수신내역 (PRVD_RCV_HIST)

역할 provider가 요청을 받고 처리한 결과다. 메시지가 중복으로 와도(at-least-once) 한 번만 처리하게 막고, 지급하지 않은 사유를 남긴다.
키 PK REQ_ID
컬럼 타입 설명
요청ID (REQ_ID) VARCHAR(200) = 디텍터아웃박스.요청ID
리워드그룹ID (RWD_GRP_ID) VARCHAR(32) 대상 리워드그룹
고객번호 (CUST_NO) VARCHAR(20) 대상 고객
이벤트일시 (EVT_DTM) TIMESTAMPTZ 소스 이벤트 시각
처리상태코드 (PRCS_STTS_CD) VARCHAR(16) PAID 지급 / REJECTED 미지급 / ERROR 오류
거절사유코드 (RJCT_RSN_CD) VARCHAR(32) 한도 초과, 1인 1회 중복, 기간 종료 등
처리일시 (PRCS_DTM) TIMESTAMPTZ 처리 시각

디텍터멱등내역과 디텍터아웃박스는 항상 1:1로 쌓이므로 하나로 합치면 쓰기 1회를 줄일 수 있다. 확정 설계(멱등 가드 후 아웃박스 입력)에 따라 분리를 유지한다.

06기존 설계 변경 사항

대상 변경 이유
리워드그룹 행 단위 조건(금액 이상, 거래유형)이 있으면 디텍터트리거조건으로 옮긴다. 누적·한도·1회·배타 조건만 남긴다 상태 없는 조건은 detector, 상태가 필요한 조건은 provider
리워드그룹 상태(중지) 컬럼이 없으면 추가한다. 중지하면 admin이 연결된 트리거도 PAUSED로 바꾼다 중지된 그룹의 요청 생성 방지
리워드항목 산정 입력값 목록을 정의한다 (예: AVG_BAL) admin이 저장할 때 디텍터필드.페이로드여부와 대조해 검증
프로모션 기간(시작·종료)과 상태가 있는지 확인한다 detector는 이벤트일시 기준, provider는 지급 시점 기준으로 검증

admin 저장 시 검증 항목

  • 디텍터필드가 rdt-db 카탈로그의 실제 컬럼·타입과 일치하는지
  • 트리거조건의 필드가 조건사용여부 = Y이고, 조건값이 데이터유형으로 변환되는지
  • 리워드항목 산정 입력값이 모두 페이로드여부 = Y 필드에 있는지
  • 멱등키순서가 지정된 필드 조합이 소스 행을 유일하게 식별하는지
  • 저장할 때마다 설정버전 +1, 디텍터설정이력에 스냅샷 기록

08확인 필요 사항

  1. 고객일별평잔에서 가입일시와 비교할 기준이 기준일자인지 적재일시인지 (디텍터기본.이벤트일시필드로 지정)
  2. 같은 프로모션에서 행 하나가 리워드그룹 여러 개를 통과하면 모두 지급하는지, 하나만 지급하는지 (provider 정책)
  3. provider가 "첫 거래" 같은 순서 의존 규칙을 이벤트일시 기준으로 판단하는지
  4. 가입 없이 전체 고객이 대상인 프로모션이 있는지 (있으면 프로모션에 대상구분 추가, 가입 조회 생략)
