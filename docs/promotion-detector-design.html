프로모션 디텍터 설계: 처리 흐름과 테이블 설계

rdt_db(CDC 읽기 전용)의 소스 테이블을 폴링해 프로모션 가입고객의 적격 이벤트만 골라 prm_db의 멱등 테이블과 아웃박스에 정확히 한 번 넣습니다. 청크 분할·claim·fencing은 기존 범위 청크 + 리스 구현 가이드를 따르고, 이 문서는 그 위에 프로모션 · 가입고객 · 다중 소스 요구를 얹습니다.

PostgreSQL 기준가입고객 300만24시간 상시EKS 다중 pod작성 2026-11-05

00전제와 가정

항목내용
rdt_dbCDC로 복제된 읽기 전용 DB. 소스 테이블마다 created_at 있음. 쓰기 불가. 인덱스 추가는 요청하면 가능하다고 가정
prm_db프로모션, 가입고객, 멱등, 아웃박스 테이블. 디텍터가 C/R/U/D 가능
규모가입고객 300만, 프로모션 수십 개 수준, 고객 1명이 여러 프로모션에 가입 가능
소스프로모션마다 읽을 소스 테이블이 다르다. 여러 프로모션이 같은 소스를 공유할 수 있다
데이터소스에는 비가입 고객 행이 섞여 있다. 가입 비율은 소스마다 다르다
운영24시간 상시. 가입은 계속 늘어난다
설계 전체의 출발점

rdt_db와 prm_db는 서로 다른 DB라 JOIN할 수 없습니다. "소스 행이 가입고객의 것인가"를 판정하는 방법이 설계의 핵심입니다.

01결론 요약

① 소스 테이블 단위로 스캔

프로모션 단위가 아니라 소스 단위로 한 번만 읽고, 그 소스를 쓰는 모든 프로모션에 결과를 나눠 줍니다. 프로모션 단위로 읽으면 같은 테이블을 N번 읽습니다.

② 청크 스캔 + 배치 가입 조회

약 1,000행 청크를 읽고 고객번호를 모아 cust_no = ANY(:arr) 1회로 판정합니다. 커버링 인덱스로 index-only scan, 청크당 수 ms입니다.

③ 고객 목록 캐시 미사용

300만 명은 메모리에 들어가지만, 캐시가 늦으면 신규 가입자 이벤트를 조용히 놓칩니다. DB 조회가 충분히 싸서 캐시의 이득보다 위험이 큽니다.

④ 가입 백필로 경합 차단

가입 커밋 직전에 처리된 청크에서 놓친 이벤트는 [가입 유효시점, planned_hwm] 구간만 고객번호로 다시 조회합니다. 시간 가정 없이 누락이 없습니다.

⑤ 멱등 키 = 프로모션 포함

(promo_id, source_id, source_pk). 소스 행 하나가 여러 프로모션의 리워드가 될 수 있습니다. 백필·재처리·재claim이 겹쳐도 중복 발행이 없습니다.

⑥ 소스별 전략 전환

가입 비율이 아주 낮은 소스만 예외로 "고객 주도 조회"로 바꿀 수 있게 filter_strategy 플래그를 둡니다.

02처리 흐름

조율(청크, 리스, 백필 대기열)은 전부 prm_db 행 잠금으로 합니다. 리더 선출이 없고 모든 pod가 같은 역할을 합니다.

2.1 Planner: 소스 단위로 청크 생성

  • poll_source 한 행 = rdt_db 소스 테이블 하나. 그 소스를 쓰는 활성 프로모션이 없으면 enabled=false로 멈춥니다.
  • 청크 크기는 행 수 기준(기본 1,000)입니다. 꼬리를 따라갈 때는 1,000행이 안 돼도 300~500ms마다 청크를 끊습니다.
  • 청크 경계의 상한은 안전 워터마크입니다.
CDC 환경의 안전 워터마크

rdt_db는 물리 복제가 아니라 CDC라서 기존 설계의 pg_last_xact_replay_timestamp()를 쓸 수 없습니다. 대신 원천 DB에 cdc_heartbeat(ts)를 1초마다 갱신하고 CDC로 같이 복제합니다.

CDC가 원천 커밋 순서대로 적용한다면 rdt_db에서 보이는 heartbeat보다 먼저 커밋된 원천 행은 모두 들어와 있습니다. safe_ts = heartbeat.ts − safety_lag이고, safety_lag는 원천 쓰기 TX 최대 지속시간 + 시계 오차보다 크게 잡습니다.

확인 필요

CDC 도구가 테이블별 병렬 적용(순서 비보장)을 한다면 테이블마다 heartbeat를 두거나 적용 지연 지표를 대신 써야 합니다.

2.2 Worker: 청크 처리

  1. claim: 기존 설계와 같습니다(FOR UPDATE SKIP LOCKED, lease_token++).
  2. 범위 조회: (created_at, pk…) > :from AND <= :to. SELECT 컬럼은 pk, created_at, cust_no, 규칙에 쓰는 컬럼만 고릅니다. 프로모션 규칙이 참조하는 컬럼의 합집합으로 자동 계산합니다.
  3. 배치 가입 조회(청크당 1회): 아래 쿼리. 커버링 인덱스 하나로 index-only scan이 됩니다.
  4. 규칙 평가(앱 메모리): 프로모션 기간, 가입 유효구간, 행 단위 조건을 확인합니다.
  5. 커밋(prm_db 단일 TX): reward_idem INSERT … ON CONFLICT DO NOTHING RETURNING → 새로 들어간 건만 outbox INSERT → poll_chunk DONE(lease_token 조건, 0행이면 롤백).
③ 가입 배치 조회 (prm_db)
SELECT cust_no, promo_id, valid_from, valid_to
FROM promo_customer
WHERE cust_no  = ANY(:custNos)           -- 청크의 distinct 고객번호 (≤1,000)
  AND promo_id = ANY(:promoIdsOfSource)  -- 이 소스를 쓰는 활성 프로모션 (앱 캐시)
  AND status   = 'ACTIVE';
④ 규칙 평가 항목조건
프로모션 기간promo.start_at <= row.created_at < promo.end_at
가입 유효구간valid_from <= row.created_at < coalesce(valid_to, ∞) — 가입 이후, 탈퇴 이전 이벤트만
행 단위 조건거래유형, 금액 하한 등. 프로모션 설정의 제한된 조건식(동등, IN, 범위)
누적 조건디텍터 범위 밖 "3회 이상", "월 합계 10만원" 등은 리워드 엔진이 처리. 디텍터를 무상태로 두어야 재처리와 병렬화가 쉽습니다.

가입자가 한 명도 없는 청크는 조회와 판정만 하고 바로 DONE 처리합니다.

2.3 처리량 감각

20~50 ms

청크 1,000행 rdt_db 범위 조회. 대부분의 시간이 여기서 듭니다.

2~5 ms

prm_db 가입 배치 조회 1회 (index-only scan).

pod × 스레드

청크가 겹치지 않으므로 소스 하나도 여러 pod가 나눠 읽습니다. 한계는 rdt_db 읽기 부하와 적중 건 쓰기입니다.

03비가입 고객 필터 전략

전략방식장점단점채택
A. 스캔 + 배치 조회소스 청크를 전부 읽고 prm_db에 고객번호 배치 조회단순. 가입 즉시 반영. 소스 인덱스는 (created_at, pk)만 필요비가입 행도 읽음기본
B. 메모리 캐시pod마다 가입자 Set/Bitmap을 들고 필터prm_db 조회 없음갱신 지연 = 누락. pod 간 버전 불일치. 무효화 설계 필요미채택
C. 고객 주도 조회cust_no = ANY(:가입자) AND created_at 구간가입자가 적으면 읽기량이 아주 작음가입자가 많으면 IN 목록 폭발. (cust_no, created_at) 인덱스 필요소스별 예외
A가 기본인 이유

배치 조회로 판정 비용을 청크당 쿼리 1회로 고정했습니다. 소스는 어차피 시간순으로 읽어야 하므로 비가입 행을 읽는 비용은 피하기 어렵습니다.

C로 바꾸는 기준

그 소스의 가입자가 수천 명 이하로 적고 유입량이 매우 커서 A의 읽기 비용이 문제일 때만. 청크·멱등·백필 구조는 그대로, 조회 쿼리만 바뀝니다.

B를 쓰지 않는 이유

캐시가 30초 늦으면 그동안 가입한 고객의 이벤트를 버립니다. 4장 백필의 전제("이후 청크는 최신 가입 정보로 조회")도 깨집니다.

04신규 가입 경합과 백필

정확성 핵심

4.1 문제

누락 시나리오
t1  Worker   : 청크 K(이벤트 created_at = 10:00:05) 가입 조회 → 고객 C 없음 → 버림
t2  가입 서비스: 고객 C 가입 커밋 (valid_from = 10:00:00)

고객 C의 10:00:05 이벤트는 리워드 대상인데 이미 버려졌습니다. 소급 가입(유효시점이 과거)이 허용되면 이 구간은 더 길어집니다.

4.2 해법: 가입 백필

  1. promo_customer.bf_status(기본 'PENDING')를 둡니다. 가입 서비스는 평소대로 INSERT만 하면 됩니다.
  2. Backfill Worker가 bf_status='PENDING' 행을 FOR UPDATE SKIP LOCKED로 가져옵니다. 부분 인덱스라 대상은 항상 작습니다.
  3. 그 프로모션의 소스마다 H = poll_source.planned_hwm을 읽습니다. 가입 행이 커밋된 뒤에 읽은 값입니다.
  4. valid_from > H.created_at이면 SKIP — 아직 청크가 없는 구간이라 정상 경로가 처리합니다.
  5. 아니면 rdt_db를 고객번호 인덱스로 조회하고 같은 규칙으로 평가 → 멱등/아웃박스 INSERT → bf_status='DONE'.
백필 조회 (rdt_db)
SELECT pk..., created_at, cust_no, <규칙 컬럼>
FROM src
WHERE cust_no = :custNo
  AND created_at >= :validFrom
  AND (created_at, pk...) <= (:H)       -- 인덱스 (cust_no, created_at)
ORDER BY created_at;

H 이하 청크: 가입 조회가 가입 커밋 전에 일어났을 수 있습니다 → 백필이 덮습니다.

H 초과 청크: H를 읽은 뒤에 계획되므로, 그 청크의 가입 조회는 가입 커밋 이후에 일어납니다 → 정상 경로가 잡습니다.

겹치는 구간은 둘 다 처리할 수 있지만 멱등 키가 중복 발행을 막습니다. 지연 시간이나 TX 지속시간에 대한 가정이 필요 없습니다.

비용

일반 가입은 valid_from ≈ 지금이고 H는 safety_lag만큼 뒤에 있어 대부분 SKIP되거나 수 초 구간만 조회합니다. 하루 10만 건 가입이어도 초당 약 1.2회 인덱스 조회입니다.

고객번호 인덱스가 없으면

PENDING 가입을 소스별로 모아 created_at >= min(valid_from) AND cust_no = ANY(:묶음)으로 범위 조회합니다. 소급 기간이 길면 비싸지므로 인덱스 요청을 선행 조건으로 둡니다.

4.3 같은 패턴을 쓰는 다른 변경

변경처리
신규 프로모션 (기존 소스 공유)start_at < planned_hwm이면 promo_backfill(promo_id, source_id, from=start_at, to=H) 생성 → promo_scope가 붙은 청크로 처리, 해당 프로모션만 평가
신규 프로모션 (새 소스)poll_source 생성, planned_hwm = (start_at, '', …)
프로모션 종료end_at 이후 이벤트는 규칙에서 제외. 활성 프로모션이 없는 소스는 HWM이 end_at을 넘은 뒤 enabled=false
탈퇴valid_to 설정 → 이후 이벤트 제외. 이미 발행된 건은 리워드 엔진 정책

프로모션 설정은 앱에서 캐시합니다. 자주 바뀌지 않고, 바뀔 때는 위 백필이 공백을 메웁니다. 캐시에 config_version을 두고 청크 처리 시작 시점에 고정해 씁니다.

05prm_db 테이블 설계

테이블역할구분
promotion프로모션 기간, 상태, 소급 허용 여부설정
promo_source프로모션 ↔ 소스 매핑 + 행 단위 규칙설정
promo_customer가입고객. 디텍터 조회용 커버링 인덱스 + 백필 대기열조회 중심
poll_source / poll_chunk소스별 HWM, 청크와 리스 (기존 설계 + 컬럼 추가)조율
promo_backfill신규 프로모션 소급 구간조율
reward_idem / outbox멱등 키, 발행 메시지결과

5.1 프로모션 설정

promotion, promo_source
CREATE TABLE promotion (
  promo_id      varchar(32) PRIMARY KEY,
  name          varchar(200) NOT NULL,
  start_at      timestamptz NOT NULL,
  end_at        timestamptz NOT NULL,
  status        varchar(16)  NOT NULL,              -- READY|ACTIVE|ENDED
  retro_allowed boolean      NOT NULL DEFAULT false, -- 소급 가입 허용 여부
  updated_at    timestamptz  NOT NULL DEFAULT now()
);

CREATE TABLE promo_source (
  promo_id   varchar(32) REFERENCES promotion,
  source_id  varchar(64) REFERENCES poll_source,
  rule_json  jsonb NOT NULL,   -- 예: {"txn_type":["PAY"],"amount_gte":10000}
  PRIMARY KEY (promo_id, source_id)
);
CREATE INDEX ix_promo_source_src ON promo_source (source_id);

규칙은 디텍터가 해석할 수 있는 제한된 조건식(동등, IN, 범위)만 허용합니다. 임의 SQL은 받지 않습니다.

5.2 가입고객: 조회 중심 설계

promo_customer
CREATE TABLE promo_customer (
  promo_id    varchar(32) NOT NULL,
  cust_no     varchar(20) NOT NULL,   -- 소스의 고객번호와 같은 타입·형식
  valid_from  timestamptz NOT NULL,   -- 리워드 대상 시작 (보통 가입 시각, DB now())
  valid_to    timestamptz,            -- 탈퇴 시각, NULL = 유지
  status      varchar(8)  NOT NULL DEFAULT 'ACTIVE',
  bf_status   varchar(8)  NOT NULL DEFAULT 'PENDING',  -- PENDING|DONE|SKIP
  joined_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (promo_id, cust_no)     -- 업무 조회: 프로모션별 가입자 목록
);

-- 디텍터 전용: 고객번호 → 가입 프로모션 (index-only scan)
CREATE UNIQUE INDEX ux_pc_detect
  ON promo_customer (cust_no, promo_id)
  INCLUDE (valid_from, valid_to, status);

-- 백필 대기열 (항상 작음)
CREATE INDEX ix_pc_bf_pending
  ON promo_customer (joined_at)
  WHERE bf_status = 'PENDING';
선두 컬럼이 cust_no인 인덱스

디텍터의 질문은 항상 "이 고객들이 어떤 프로모션에 가입했나"입니다. PK (promo_id, cust_no)만 있으면 cust_no = ANY 조회가 프로모션 수만큼 인덱스를 훑습니다.

INCLUDE로 테이블 접근 제거

규칙 평가에 필요한 유효구간·상태가 인덱스에 있어 heap을 읽지 않습니다. visibility map이 최신이어야 하므로 autovacuum을 공격적으로 둡니다(autovacuum_vacuum_insert_scale_factor 낮춤).

고객 × 프로모션 = 1행 (정규화)

고객 1행에 promo_ids[] 배열로 두면 가입/탈퇴마다 같은 행을 갱신해 경합과 bloat가 생기고, 프로모션별 유효구간 표현이 어렵습니다.

용량

300만 × 평균 2~3개 = 600만~900만 행. heap 약 0.6~0.9GB, 디텍터 인덱스 약 0.4~0.6GB. 메모리에 올라가는 크기라 파티셔닝 불필요. 수천만 행을 넘기면 cust_no 해시 파티션(8~16개).

고객번호 형식은 소스와 완전히 같게

타입, 자릿수, 앞자리 0 처리가 다르면 조회가 조용히 빗나갑니다. 소스마다 형식이 다르면 소스 설정에 정규화 함수를 지정합니다. valid_from은 앱 시각이 아닌 DB now()로 넣고, 소급 가입일 때만 과거 값을 허용합니다.

5.3 조율 테이블 (기존 설계에 추가)

poll_source, poll_chunk 추가 컬럼 · promo_backfill
ALTER TABLE poll_source
  ADD COLUMN filter_strategy varchar(16) NOT NULL DEFAULT 'SCAN';  -- SCAN|CUSTOMER

ALTER TABLE poll_chunk
  ADD COLUMN promo_scope varchar(32);   -- NULL=정상 청크, 값=해당 프로모션 백필 청크

CREATE TABLE promo_backfill (
  backfill_id  bigserial PRIMARY KEY,
  promo_id     varchar(32) NOT NULL,
  source_id    varchar(64) NOT NULL,
  from_key     text[] NOT NULL,
  to_key       text[] NOT NULL,          -- 생성 시점의 planned_hwm
  status       varchar(16) NOT NULL DEFAULT 'READY',  -- READY|PLANNED|DONE
  created_at   timestamptz NOT NULL DEFAULT now()
);

Planner가 promo_backfill 구간을 promo_scope가 붙은 청크로 잘라 넣고, 워커는 같은 경로로 처리하되 그 프로모션만 평가합니다. 정상 처리 지연을 막기 위해 백필 청크의 max_pending을 따로 둡니다.

5.4 멱등 · 아웃박스

reward_idem
CREATE TABLE reward_idem (
  promo_id     varchar(32) NOT NULL,
  source_id    varchar(64) NOT NULL,
  source_key   text        NOT NULL,   -- 소스 PK 값의 JSON 배열 인코딩
  cust_no      varchar(20) NOT NULL,
  event_at     timestamptz NOT NULL,   -- 소스 created_at
  created_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (promo_id, source_id, source_key)
) PARTITION BY LIST (promo_id);        -- 프로모션 종료 후 파티션 단위 정리
  • 파티션 키가 promo_id라 프로모션이 끝나고 보관 기간이 지나면 DETACH/DROP 한 번으로 정리됩니다. 아주 큰 프로모션은 event_at 월 단위 하위 파티션을 씁니다.
  • 아웃박스는 기존 구현을 그대로 씁니다. 페이로드: promo_id, cust_no, source_id, source_key, event_at + 규칙 평가에 쓴 값.
  • 메시지 키를 cust_no로 두면 Kafka 파티션 안에서 고객별 순서가 유지되어 리워드 엔진의 누적 계산이 쉬워집니다.

07다중 pod 운영

리더 없음

모든 pod가 Planner, Worker, Backfill Worker를 함께 돌립니다. 조율은 prm_db 행 잠금(SKIP LOCKED)과 리스로 합니다.

커넥션 풀 분리

rdt_db용과 prm_db용을 분리합니다. rdt_db 풀 크기가 곧 소스 읽기 동시성 상한입니다.

소스 간 공정성

워커는 소스를 라운드로빈으로 돌며 claim하고, 소스별 동시 claim 상한을 둡니다. 유입이 큰 소스가 작은 소스를 굶기지 않습니다.

스케일 아웃 신호

소스별 안전 워터마크 − 처리 완료 워터마크가 목표(예: 10초)를 넘으면 HPA로 pod를 늘립니다.

09확인 필요 사항

  • CDC 도구와 적용 순서 보장 여부(Debezium, DMS, OGG 등). 안전 워터마크 방식이 달라집니다.
  • rdt_db에 (cust_no, created_at) 인덱스 추가가 가능한가.
  • 소급 가입(가입 전 이벤트 인정) 정책이 있는가. 있다면 최대 소급 기간은.
  • 누적·한도 조건을 리워드 엔진이 처리하는가(이 설계는 그렇게 가정).
  • 소스 테이블마다 고객번호 컬럼명·형식이 같은가.
  • 소스별 유입량(TPS)과 가입자 비율. pod 수와 청크 크기 산정에 씁니다.
