Read-Only 소스 병렬 폴링 · 쉬운 설명

범위 청크와 리스 동작 원리

여러 pod가 하나의 소스 테이블을 나눠 읽을 때, 중복 없이, 누락 없이, pod가 죽어도 이어서 처리하는 방법을 물류센터에 빗대어 설명합니다.

소스 데이터를 번호표 붙은 작업 바구니로 나누고, 워커는 바구니를 하나씩 기한을 정해 빌려가서(리스) 처리한 뒤 반납합니다.

01비유: 택배 물류센터

계속 택배가 들어오는 물류센터가 있고, 직원 여러 명이 함께 일한다고 생각해 보세요.

물류센터우리 시스템
계속 들어오는 택배소스 테이블에 쌓이는 행
택배를 1,000개씩 묶은 바구니청크: “여기부터 여기까지”라는 범위
바구니를 만드는 분류 담당자Planner
바구니를 가져가 처리하는 직원들Worker: 여러 pod의 여러 스레드
바구니 목록이 적힌 화이트보드poll_chunk 테이블
“김씨가 10분 동안 가져감”이라는 대여 기록리스(lease)
대여할 때마다 새로 받는 대여 번호fencing token (lease_token)

02청크란?

소스 테이블을 시간순으로 줄 세운 뒤, 일정한 크기로 잘라 놓은 구간입니다.

청크 11–1000
청크 21001–2000
청크 32001–3000
청크 43001–3500
아직 안 자름계속 증가 →
오래된 행새 행

청크는 데이터를 복사한 것이 아니라 범위 정보만 담은 메모입니다. 예를 들면 “08:00:00부터 08:00:03 사이의 행”입니다.

청크끼리는 범위가 겹치지 않습니다. 그래서 서로 다른 청크를 처리하는 워커들은 같은 행을 볼 일이 없습니다.

화이트보드(poll_chunk)에 적힌 내용

청크범위상태가져간 사람반납 기한대여 번호
11–1000완료––1
21001–2000처리 중pod-A10:051
32001–3000처리 중pod-B10:061
43001–3500대기––0

03리스란?

리스는 기한이 있는 대여입니다. 워커는 청크를 영원히 가져가지 않고, “10분 동안 내가 처리할게”라고 빌려갑니다. 이렇게 하는 이유는 pod가 죽는 경우 때문입니다.

기한pod-A가 청크 2를 가져간 뒤 죽으면결과
없음청크 2가 영원히 “처리 중”으로 남음누락
있음10분이 지나도 완료되지 않은 청크는 다른 워커가 다시 가져감자동 복구

04전체 흐름

  1. Planner
    “새 데이터가 1,000개 쌓였네” → 화이트보드에 청크 5를 추가합니다. 상태는 대기입니다.
  2. Worker
    화이트보드에서 대기 중인 청크 하나를 집어 처리 중으로 바꿉니다. 가져간 사람, 반납 기한, 대여 번호를 함께 기록합니다.
  3. Worker
    소스 테이블에서 그 범위만 읽습니다.
  4. Worker · 하나의 트랜잭션
    아래 세 가지를 한 번에 처리합니다.
    • 멱등 테이블에 기록
    • 아웃박스에 이벤트 저장
    • 화이트보드의 청크를 완료로 변경

처리가 끝나면 워커는 2단계로 돌아가 다음 청크를 가져갑니다.

05동시성 문제를 막는 방법

문제 1

두 워커가 같은 청크를 동시에 집으면?

FOR UPDATE SKIP LOCKED가 막아 줍니다. 규칙은 이렇습니다.

누가 이미 손대고 있는 바구니는 기다리지 말고 건너뛰고, 다음 바구니를 집는다.
pod-A청크 4를 잡음청크 4
pod-B청크 4는 잠겨 있어 건너뜀 → 청크 5를 잡음청크 5
pod-C4, 5 모두 잠겨 있어 건너뜀 → 청크 6을 잡음청크 6

서로 기다리지 않으니 빠르고, 같은 청크를 집지 않으니 중복이 없습니다.

문제 2

pod가 처리 도중 죽으면?

  1. 10:00pod-A가 청크 2를 가져감반납 기한 10:10
  2. 10:03pod-A 죽음
  3. 10:10반납 기한 지남
  4. 10:11pod-B가 기한 지난 청크 2를 다시 가져가 처음부터 처리

소스가 append-only라서 같은 범위를 다시 읽으면 같은 데이터가 나옵니다. 그래서 처음부터 다시 처리해도 안전합니다.

문제 3

죽은 줄 알았던 pod가 다시 살아나면? (좀비)

가장 까다로운 경우입니다. 대여 번호(fencing token)로 막습니다.

  1. 10:00pod-A가 청크 2를 가져감대여 번호 1번
  2. 10:03pod-A가 멈춤GC나 네트워크 문제 등. 죽은 것은 아님
  3. 10:11기한이 지나 pod-B가 청크 2를 다시 가져감대여 번호 2번
  4. 10:12pod-B: “대여 번호 2번인 청크 2를 완료로 바꿔줘” → 성공
  5. 10:13pod-A가 깨어나 “대여 번호 1번인 청크 2를 완료로 바꿔줘” → 지금 번호는 2번이라 0건 변경 → 롤백pod-A가 저장하려던 아웃박스 이벤트도 함께 취소됨
청크 완료 처리와 아웃박스 저장은 하나의 트랜잭션입니다. 대여 번호가 틀리면 완료 처리가 실패하고, 아웃박스 저장도 같이 취소됩니다.

혹시 이 단계까지 뚫리더라도 멱등 테이블이 같은 행의 중복 저장을 한 번 더 막습니다. 안전장치가 두 겹입니다.

06다른 방식과 비교

방식비유결과
워커 하나가 커서 하나로 처리직원 1명이 모든 택배 처리느림. 그 사람이 쓰러지면 전부 멈춤
“짝수는 A, 홀수는 B”로 나눔모든 직원이 택배 더미 전체를 뒤져서 자기 것만 고름각자 전체를 훑어야 해서 낭비. 직원 수가 바뀌면 규칙을 다시 짜야 함
범위 청크 + 리스바구니로 나눠 놓고 손이 빈 사람이 가져감빠름. 직원 수가 늘거나 줄어도 그대로 동작. 쓰러져도 자동 복구

특히 pod 수가 바뀌어도 설정을 바꿀 필요가 없습니다. pod가 늘면 바구니를 집는 손이 늘어날 뿐입니다.

07기억할 세 가지

청크

겹치지 않는 범위. 같은 데이터를 두 번 읽지 않습니다.

리스

기한 있는 대여. pod가 죽어도 자동으로 다시 처리됩니다.

대여 번호 + 단일 트랜잭션

좀비 pod가 있어도 결과는 정확히 한 번만 반영됩니다.
